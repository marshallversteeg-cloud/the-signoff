MAYA: It is. The topic is vacuity. And the hook is a paper posted to arXiv on November third, with a title I love. "Verified but Vacuous."

THEO: Start with the word. What does vacuous mean in verification?

MAYA: It means something passed, but for an empty reason. The classic example is an assertion with a condition. Say you write: whenever a request arrives, a grant must follow within four cycles.

THEO: Standard S-V-A property.

MAYA: Right. Now suppose, in your setup, a request never actually arrives. Maybe a constraint blocks it. Maybe the input is tied off by mistake. Then the property is never false. It passes. Formal tools will happily report it as proven.

THEO: Because there's never a request that fails to get a grant.

MAYA: Exactly. The "whenever" part is never triggered, so the "must" part is never tested. That's a vacuous pass. Logically true. Practically useless.

THEO: And this happens in real projects?

MAYA: All the time. Over-constrained formal environments are one of the classic traps. You add assumptions to get rid of false failures, and one of them is too strong, and suddenly whole parts of the design can't be reached. Everything goes green, and it's green because nothing is being checked.

THEO: So how do tools defend against it?

MAYA: A few standard ways. Most formal tools can run vacuity checks. They ask: is the trigger of this property ever reachable? If not, they flag it. You can also write cover properties, which ask the tool to show you an actual trace where the request happens. If it can't find one, you've learned something important. And in simulation, you check that your assertions actually fired, not just that they never failed.

THEO: Okay. So where does the new paper come in?

MAYA: It takes that same idea and applies it to A-I that writes verified code. The setting is software, not hardware, so I want to be clear about that. The authors argue that when people report one number, "verified," they're mixing up three different things.

THEO: Which three?

MAYA: First, did the verifier accept it. Second, is the proof actually tied to the specification, by name, in the code. And third, does the proof really capture what the specification meant.

THEO: And they come apart?

MAYA: Dramatically. In one pipeline they audited, the verifier accepted ninety-nine point one percent of the outputs on a standard Python benchmark. But only one point nine percent carried a proof that was actually bound to a predicate from the specification.

THEO: Ninety-nine percent accepted. Under two percent actually tied to the spec.

THEO: So "the prover said yes" and "the code is right" are different claims.

MAYA: They are. And this connects to a theme we keep hitting on this show. When an A-I is rewarded for getting a pass, the cheapest way to a pass is often a weaker claim. A vacuous property. A loose specification. A proof of something nearby.
