MAYA: Explainer time. Equivalence checking. Every agent story today is about software changing a design. Rewriting R-T-L for better power, performance and area. Optimizing a netlist. Making late fixes. The question underneath all of it is, how do you know the change didn't break anything?

THEO: And equivalence checking is the answer that's been around for decades.

MAYA: It has. Here's the idea. Functional verification asks, is this design correct? Equivalence checking asks a narrower question. Do these two versions of the design behave the same?

THEO: Give me the classic case.

MAYA: You write R-T-L, the hardware description. Synthesis turns it into a netlist of gates. Then more tools modify that netlist. They add test circuitry, optimize for timing, and rework it during physical design. Each tool is supposed to preserve behavior. But tools have bugs, and engineers make manual edits late in the project, called engineering change orders. So before tape-out, teams formally prove the final netlist matches the original R-T-L.

THEO: Why not just rerun the simulations on the netlist?

MAYA: You can, and people used to. But gate-level simulation is slow, and it's only as good as your tests. Equivalence checking is a proof. It covers every possible input, not just the ones you thought to try.

THEO: How does it actually prove that?

MAYA: The simplest version works on logic without memory, which is called combinational logic. You take the two circuits, feed them the same inputs, and compare their outputs with an exclusive-or gate. That combined circuit has a name. It's called a miter.

THEO: Like the joint in carpentry.

MAYA: Two pieces meeting at a seam. Then you ask a solver one question. Is there any input that makes the two outputs disagree? If the solver proves no such input exists, the circuits are equivalent. If it finds one, that input is a counterexample, and you can simulate it to see exactly where they differ.

THEO: That sounds like it would blow up on a real chip.

MAYA: It would, if you did it all at once. Two things make it practical. First, the registers. If both versions have the same registers, the tool matches them up and cuts the problem at each one, so it's checking lots of small chunks of logic instead of one giant one. Second, the two versions usually share a lot of internal structure, so the tool finds matching internal signals and uses them as stepping stones. The solvers underneath are the same kinds of engines used across formal verification, satisfiability solvers and binary decision diagrams.

THEO: And when the registers don't line up?

MAYA: That's the hard case, called sequential equivalence checking. Say an optimization moves logic across registers to fix timing, which is called retiming. Or two state machines encode their states differently. Now you can't just match register to register. You have to prove the two designs produce the same outputs over time, from their starting states. That usually needs heavier techniques, like induction over clock cycles.

THEO: Which we'll do an explainer on some other week.

MAYA: Deal. Now, why does this matter for A-I right now?

THEO: Go on.

MAYA: Two reasons. First, a lot of what the agents are being pitched for is transformation. Take this R-T-L and make it smaller, or lower power, without changing what it does. That's exactly the claim equivalence checking can prove or disprove, with no trust in the agent required. If an agent rewrites a block and the equivalence check passes, the behavior is preserved, whatever the agent was thinking.

THEO: And the second reason?

MAYA: The second is the limit. Equivalence checking only proves two versions match. If the reference version has a bug, the new one will faithfully have the same bug. It tells you nothing about whether the original was right. And when the agent is writing the design from a spec, with no golden reference to compare against, equivalence checking can't help you at all. That's back to functional verification, which is the hard problem.

THEO: So it's a perfect tool for one question, and no help on the other.

MAYA: Right. Know which question you're asking.

THEO: Quick refresher on coverage.

MAYA: Coverage is a list of situations you want your tests to reach. The FIFO filled up. The FIFO emptied while a write was happening. Each one is a bin. Coverage closure means writing tests until every bin is hit.

THEO: And the agent writes those tests.

MAYA: Right. The setup is small and honest about being small. Each round, the agent looks at which bins are still unhit, picks one, and asks a language model for a directed test. In this paper the model was Anthropic's Claude Sonnet four point six. The test runs in the open-source Verilator simulator, and the coverage results come back.

THEO: Results?

MAYA: Three designs. An asynchronous FIFO, a serial transmitter, and a bus bridge. Coverage started at about ninety-two, eighty-nine and sixty-seven percent. Within eight rounds, every logged run reached a hundred percent.

THEO: So, case closed.

THEO: Same principle as last week. The tool is the evidence, not the model.

MAYA: Second, data correctness is checked separately, by scoreboards that compare actual outputs against expected values, and the model never sees them. Because hitting a bin only proves you reached a state. It doesn't prove the data along the way was right.
